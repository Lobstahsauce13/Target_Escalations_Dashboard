# Target Escalation Dashboard

Live site: https://target-escalations-dashboard.zy8dcr9n7z.workers.dev

Built on the Best Buy dashboard v4: same framework and styling. One page with four tabs:

- **Escalations**: Target's CM work orders from Maximo (`index.html`). **Add Escalation**, at the right end of the pill row, types in a new one.
- **No Show**: the BDS No Show and Data Review tracker on its own (`index.html`).
- **Store Visits** and **Directory**: from v4 (`visits.html`, shown in a frame under the shared header), now fed by the Power BI export.

The banner holds the title, the four tabs, the Save button (while there are unsaved tracker changes) and the five imports. The import page shows one small square per file, named for its file with a line saying what it fills in; click a square to pick the file:

- **export** is Maximo's work order export. It fills the escalation list and each work order's details. It's recognized by its column headings (`work_order_number`, `work_type`, `site`, ...), so the file name doesn't matter. Only CM rows are loaded; PM rows are skipped, and a file with no CM rows stops the import. Status codes: APPR = New, VDECWO = Open, VINPRG = Completed, VDECWC = Closed, not removed. A status code not on that list, a missing column, or a date not in Maximo's format (`09/30/2026 06:28 AM EDT`) stops the import with a message, and nothing is loaded. A work order is past due when its LOS Finish (`repair_by`) has passed and it's New or Open. The list is sorted by LOS Finish, oldest first. The search box takes a store # or a work order #. The header's street address links to Google Maps. Each work order shows its Problem Code (`problem`) as a pill in the header, then, as rounded tiles side by side, its status, Status Date (`earliest_start`), Report Date (`arrive_by`) and LOS Finish (`repair_by`). Vendor Work Validation (`vendor_wo_val`) shows only when it isn't Pass, in red when it's Fail. Reply opens an email draft to the DM or the PML with the work order's facts, To line blank; the PML's draft leaves out rep names.
- **data** is Power BI's export (sheet "Export"). It fills each store's rep, DM (`FOM Territory`) and whether the rep visited that week. Only the Target Break-Fix Continuity form is kept, and only the waves that have started (this week and earlier). Stores are matched to Maximo by Chain Store # (the site without its "T"). Power BI has no status column, so a visit is Completed once its report is entered, else Sched this week when its date falls this week. Dates are read as the serial numbers in the file, because SheetJS shifts date cells by the time zone's old offset. A Power BI export is cut off at 150,000 rows, so filter it to Target and the recent weeks. The file is read once, by the Store Visits frame; each escalation's "Rep & Visits" card asks the frame for the store's last four weeks, and the header shows the store's street address from it. The export's sheet unpacks to hundreds of MB, so `data-reader.js` reads it in the background, one row at a time, keeping only Target Break-Fix Continuity rows (opening it whole froze the tab for about 35 seconds and could run Chrome out of memory). The box shows the row it's on while it reads. In the Store Visits table, Revisit? shows a red check for any kind of revisit and is blank otherwise. The data file also fills the Directory: every rep with a Target visit, their mobile and home phone, manager (`Reps Manager`) and DM, and their week, which adds the other Target projects scheduled this week (the reader keeps those rows too). No email is shown. Every rep name on the page (Rep & Visits, Tracker Notes, the Store Visits table) opens that rep on the Directory; names typed in the tracker link only when they match a rep in the data file exactly.
- **Interactives Program Presence and Functionality** is the report CS emails out. It fills each escalation's "Rep's Answers" card: the store's visit date, how many displays are present and working, and every display answered No (its DPCI number, then the display name in bold, then the reason given). On Store Visits it fills the store header's display compliance counts (present, not present, working, not working). With no store picked it also fills the Presence & Functionality graph for the nation and each region, counted like the file's own calculator: presence is Yes out of every display, functionality is Yes out of the displays with an answer. A picked store shows only its own counts, no graph. Only its "Presence and Functionality" sheet is read, from the row headed Visit Date down; the trend and pivot sheets are ignored. Stores are matched to Maximo by Store # (the site without its "T"). A display whose DPCI number appears in the work order's description is listed first and marked. A missing column, or a Present? answer that isn't Yes or No, stops the import.
- **BDS No Show and Data Review** is the tracker kept by hand. It fills each escalation's "Tracker Notes" card: Comments, Action on Maximo, In Maximo, Closed in Maximo, Rep, FOM (DM), the date of the update to the FOM and PML, whether the status was emailed, and the response. Every sheet with Work Order and "Response from FOM or PML" headings is read (No show and Data Review); rows match by work order number, and by Site for the store overview. It also fills the No Show tab, its Responses sheet gives the log notes, and it is the one file Save writes to.
- **Parts Orders Detail** lists parts ordered for Target stores. It fills each escalation's "Parts" card with that store's orders, newest first: part, reason, order date, status (Ordered, Shipped, Canceled or Troubleshooting only) and the tracking number, linked to FedEx tracking. Its Ticket ID isn't a work order number, so orders match by store (Chain Store Number).

Everything is read in the browser. The tracker is the one file the dashboard writes to (see below); the other four are read only. Display preferences (theme, open tab, open filter panels) are remembered.

## Editing the tracker and saving it back

Each Tracker Notes card (on an escalation and on No Show) has an **Edit** button for its hand-kept fields: Comments, Action on Maximo, In Maximo, Closed in Maximo, Rep, FOM (DM), Update to FOM & PML, Status Emailed to FOM and Response from FOM or PML. A changed field shows **Unsaved** until **Save N Changes to the Tracker** in the banner writes it into the same file. Closing the tab with unsaved changes warns first.

- Saving needs Chrome or Edge: the tracker square opens the file with the browser's file picker, and the first Save asks permission to write to it. In other browsers the file is still read, and Save says it needs Chrome or Edge.
- Save rewrites only the changed cells (and added rows) in that sheet's XML inside the .xlsx (`xlsx-save.js`). Formatting, filters, column widths, the other sheets and every other cell stay byte for byte as they were. A new cell takes the style of the cell above it. Text goes in as text; Update to FOM & PML goes in as an Excel date.
- A field left as it was is never rewritten: Excel's line breaks, a trailing space ("Y ") and a date's time of day all count as unchanged. Update to FOM & PML gets a date picker when the cell is a date or empty; a cell holding text (often several dates, one per line) stays a text box.
- If the file changed on disk since it was opened (someone saved it in Excel), Save stops and asks to open it again, so no row is written in the wrong place. If Excel has the file open and locked, Save says to close it there.

**Add Escalation** asks for the work order number, store, Problem Code (BDS_NO_SHOW or BDS_DATA_REVIEW), description, Status Date, Report Date and LOS Finish, plus the rep and FOM (DM), filled in from the data file's store when it's loaded. The work order joins the escalation list as New, marked **Added by Hand**, and becomes a new row on the tracker's No show or Data Review sheet (by its Problem Code), right after that sheet's last row. Dates are written as text like Maximo's (`10/09/2026 05:00 PM`). It needs the tracker loaded, and a work order number already in the list or the tracker is refused.

## No Show

The No Show tab reads only the BDS No Show and Data Review file. The left side lists every row of its No show and Data Review sheets, newest Status Date first (300 at a time, with a button for more), searchable by store number, work order number, or a name or word in Rep, FOM, Description, Comments or Response. The pill row counts No Show and Data Review rows, Open in Maximo (Closed in Maximo isn't Y), Not Emailed, Waiting on Response (emailed, no response yet) and Responded; each pill filters the list.

With no row open it shows a summary: totals, rows by month for the last 12 months, the stores and reps named most in that time (a store opens its rows; a rep opens in the Directory), and the Responses sheet's log notes, each with a Copy button. A row opens with its Maximo fields as tiles, its Tracker Notes (editable, as above), the store's other rows, and links to the work order on Escalations (when it's in the export file) and the store on Store Visits.

Every push to `main` publishes the site to the Cloudflare Worker `target-escalations-dashboard` through GitHub Actions (`.github/workflows/deploy.yml`). It needs two repository secrets under Settings > Secrets and variables > Actions: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. You can also rerun it from the Actions tab. The Worker serves `index.html`, `visits.html`, `data-reader.js` and `xlsx.full.min.js`; `.assetsignore` keeps the other repo files off the site. Cloudflare's own Git integration (Workers Builds) on this Worker must be disconnected so only one thing deploys.

## Store overview

Picking a store on Store Visits (search its number, or click it in the list) shows its display compliance counts in the header and, above its assignments: Rep's Answers, Rep & Visits, the store's escalations (each opens on Escalations), every tracker row for the store, and its parts orders with tracking links.

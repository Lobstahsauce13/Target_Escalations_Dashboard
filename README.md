# Target Escalation Dashboard

Live site: https://target-escalations-dashboard.zy8dcr9n7z.workers.dev

Built on the Best Buy dashboard v4: same framework and styling. One page with three tabs:

- **Escalations**: Target's CM work orders from Maximo (`index.html`). Read only for now.
- **Store Visits** and **Directory**: from v4 (`visits.html`, shown in a frame under the shared header), now fed by the Power BI export.

The banner holds the title, the three tabs and the six imports. Each import box is named for its file and says what it fills in:

- **export** is Maximo's work order export. It fills the escalation list and each work order's details. It's recognized by its column headings (`work_order_number`, `work_type`, `site`, ...), so the file name doesn't matter. Only CM rows are loaded; PM rows are skipped, and a file with no CM rows stops the import. Status codes: APPR = New, VDECWO = Open, VINPRG = Completed, VDECWC = Closed, not removed. A status code not on that list, a missing column, or a date not in Maximo's format (`09/30/2026 06:28 AM EDT`) stops the import with a message, and nothing is loaded. A work order is past due when its LOS Finish (`repair_by`) has passed and it's New or Open. The list is sorted by LOS Finish, oldest first. The search box takes a store # or a work order #. Each work order shows its Problem Code (`problem`) as a pill in the header, then Status Date (`earliest_start`), Report Date (`arrive_by`) and LOS Finish (`repair_by`). Vendor Work Validation (`vendor_wo_val`) shows only when it isn't Pass, in red when it's Fail. Reply opens an email draft to the DM or the PML with the work order's facts, To line blank; the PML's draft leaves out rep names.
- **data** is Power BI's export (sheet "Export"). It fills each store's rep, DM (`FOM Territory`) and whether the rep visited that week. Only the Target Break-Fix Continuity form is kept, and only the waves that have started (this week and earlier). Stores are matched to Maximo by Chain Store # (the site without its "T"). Power BI has no status column, so a visit is Completed once its report is entered, else Sched this week when its date falls this week. Dates are read as the serial numbers in the file, because SheetJS shifts date cells by the time zone's old offset. A Power BI export is cut off at 150,000 rows, so filter it to Target and the recent weeks. The file is read once, by the Store Visits frame; each escalation's "Rep and visits" card asks the frame for the store's last four weeks, and the header shows the store's street address from it. The export's sheet unpacks to hundreds of MB, so `data-reader.js` reads it in the background, one row at a time, keeping only Target Break-Fix Continuity rows (opening it whole froze the tab for about 35 seconds and could run Chrome out of memory). The box shows the row it's on while it reads. In the Store Visits table, Revisit? shows a red check for any kind of revisit and is blank otherwise.
- **Interactives Program Presence and Functionality** is the report CS emails out. It fills each escalation's "Rep's answers" card: the store's visit date, how many displays are present and working, and every display answered No with the reason given. Only its "Presence and Functionality" sheet is read, from the row headed Visit Date down; the trend and pivot sheets are ignored. Stores are matched to Maximo by Store # (the site without its "T"). A display whose DPCI number appears in the work order's description is listed first and marked. A missing column, or a Present? answer that isn't Yes or No, stops the import.
- **People Report** is the rep directory. It fills the Directory tab's rep details.
- **BDS No Show and Data Review** is the tracker kept by hand. It fills each escalation's "Tracker notes" card: Comments, Action on Maximo, In Maximo, Closed in Maximo, Rep, FOM (DM), the date of the update to the FOM and PML, whether the status was emailed, and the response. Every sheet with Work Order and "Response from FOM or PML" headings is read (No show and Data Review); rows match by work order number.
- **Parts Orders Detail** lists parts ordered for Target stores. It fills each escalation's "Parts" card with that store's orders, newest first: part, reason, order date, status (Ordered, Shipped, Canceled or Troubleshooting only) and the tracking number, linked to FedEx tracking. Its Ticket ID isn't a work order number, so orders match by store (Chain Store Number).

Everything is read in the browser. No workbook data is saved; only display preferences (theme, open tab, open filter panels) are remembered. There is no export.

Every push to `main` publishes the site to the Cloudflare Worker `target-escalations-dashboard` through GitHub Actions (`.github/workflows/deploy.yml`). It needs two repository secrets under Settings > Secrets and variables > Actions: `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. You can also rerun it from the Actions tab. The Worker serves `index.html`, `visits.html`, `data-reader.js` and `xlsx.full.min.js`; `.assetsignore` keeps the other repo files off the site. Cloudflare's own Git integration (Workers Builds) on this Worker must be disconnected so only one thing deploys.
